# Learning System and Local OCR Architecture

Status: proposal, 2026-08-17
Scope: make the current trainer coherent first; add local worksheet recognition second. No application code is changed by this document.

## Recommendation in one page

The system should have one product loop:

> **Plan → Learn → Practise → Check → Diagnose → Review → Re-check**

Math, English, Chinese, speed drills, diagnostics, and OCR should be entry points into that loop—not separate mini-products with separate ideas of progress.

The key architectural move is to create a shared learning core around five concepts:

1. **Skill graph** — the curriculum, prerequisites, and observable subskills.
2. **Item bank** — questions/tasks tagged to skills, difficulty, representation, and misconception.
3. **Attempt event** — every answer, hint, elapsed time, correction, or uploaded worksheet result.
4. **Mastery projection** — an explainable current estimate derived from attempts, not a second source of truth.
5. **Review queue** — the next best small set of work, with a reason a parent can understand.

OCR belongs at the boundary: it converts a worksheet image into proposed structured attempts. It must not become the curriculum, the grader, or the learner model. For worksheets generated by this app, embed a page/QR identifier and retain the answer key; then OCR only needs to read the child's answer regions. This is much safer and easier than trying to rediscover the full question from pixels.

For this ARM64 Mac mini, start with **Apple Vision as a zero-download printed-text baseline** and benchmark **GLM-OCR 0.9B through MLX** as the first dedicated local document model. Its official guide targets Apple Silicon, uses Metal, and says the model should fit in 8 GB unified memory. Test PaddleOCR as a modular challenger, but current PaddlePaddle macOS support is CPU-only, so do not assume it will be the fastest option. Keep Mathpix only as an optional cloud benchmark, not a local dependency.

## What Yuanfudao publicly shows—and what it does not

These are public product descriptions and vendor claims, not evidence of proprietary internals.

- An official Yuanfudao course page describes a whole-term loop around “问、预、学、练、复”: pre-class learning diagnosis and planning, in-class response feedback, post-class reports and individualized practice, followed by problem localization and targeted resources. It also lists term-start diagnosis, mid-term re-diagnosis, post-exam paper analysis, and parent/teacher feedback ([official course page](https://www2.yuanfudao.com/mkt/999373/combo?lessonId=13426838)). Another official page describes “教、练、测” with lesson entry/exit checks ([official course page](https://www.yuanfudao.com/mkt/68530/combo)).
- The current XiaoYuan AI site presents a content-and-feedback loop: photo homework checking, automatic error marking, cause analysis, explanations, a wrong-question book, improvement plans, and similar-question practice. It also advertises curriculum-synchronized “learn one lesson, practise one lesson” content ([official XiaoYuan AI page](https://kousuan.yuanfudao.com/)).
- The same page claims a 3-billion-question bank, 100+ homework question types, and a photo-search hit rate above 98%. These are vendor-reported numbers, not independent benchmarks ([official XiaoYuan AI page](https://kousuan.yuanfudao.com/)).
- The official XiaoYuan learning-device site lists OCR/image recognition and knowledge graphs among its capabilities, but does not disclose model architecture, ranking/recommendation algorithms, training data, deployment topology, or mastery equations ([official site](https://megrez-ng-bj.yuanfudao.com/)).
- The XiaoYuan search privacy policy confirms that camera/gallery images are processed for question search and practice. It does not establish how OCR, retrieval, or grading work internally ([official privacy policy](https://xyst.yuanfudao.com/user-profile/api/privacy-policy/solar-user-privacy-xyst.html)).

The useful lesson is therefore a **public product pattern**, not a copied implementation:

> curriculum-aligned content → short learning/practice unit → answer/photo capture → correction and error tagging → targeted re-practice → learner/parent report

The important advantage is not “more buttons” or even “more questions.” It is that every activity feeds the same learner model and produces a clear next action.

## Why this repository currently feels fragmented

The current code has good components, but progress is stored by feature:

- math sessions, wrong answers, and mastered multiplication facts are separate tables in [`001_init.sql`](../../internal/db/migrations/001_init.sql);
- curriculum status and four rubric scores live in [`003_curriculum.sql`](../../internal/db/migrations/003_curriculum.sql);
- Chinese review statistics and rounds have their own model in [`004_chinese.sql`](../../internal/db/migrations/004_chinese.sql) and [`005_chinese_review_v2.sql`](../../internal/db/migrations/005_chinese_review_v2.sql);
- English curriculum uses its own progress store in [`007_english_curriculum.sql`](../../internal/db/migrations/007_english_curriculum.sql).

That is reasonable historically, but it means there is no single answer to: “What is she learning this week, what evidence do we have, and what should she do next?”

Do not rewrite these tables immediately. Add a compatibility layer and migrate incrementally.

## Target domain model

### Stable curriculum layer

`Skill`

- `skill_id`: stable across UI renames, e.g. `math.p4.decimals.compare`
- grade, subject, strand, prerequisites
- child-facing success statement in English
- parent coaching note (Chinese may remain here)

`LearningObjective`

- connects syllabus/textbook units to one or more skills
- carries source and confidence; avoids treating a textbook chapter as a skill

### Content layer

`Item`

- stable item ID and revision
- prompt/diagram assets, response type, canonical answer/evaluator
- skill weights, difficulty, representation, source/provenance
- misconception tags and worked-solution steps

`ItemVariant`

- parameterized values generated from a reviewed template
- deterministic seed so an attempt can always be reproduced

This is where a serious question bank differs from a folder of exercises: every item has instructional metadata and a reliable evaluator.

### Evidence layer

`LearningEvent` should be append-only:

```json
{
  "eventId": "...",
  "learnerId": "daughter",
  "occurredAt": "...",
  "activityId": "...",
  "itemId": "math.p4.decimals.compare.014",
  "skillEvidence": [{"skillId": "math.p4.decimals.compare", "weight": 1.0}],
  "response": {"raw": "3.40 > 3.4", "normalized": "false"},
  "outcome": "incorrect",
  "elapsedMs": 18000,
  "help": {"hintCount": 1, "solutionSeen": false},
  "capture": {"method": "worksheet_ocr", "confidence": 0.87, "confirmedBy": "parent"}
}
```

An OCR result is initially a **proposal** linked to image regions and model version. It becomes mastery evidence only after deterministic validation plus a confidence policy, or explicit confirmation.

### Derived learner layer

`SkillState`

- readiness/mastery band, uncertainty, last evidence date
- separate concept, accuracy, fluency/speed, and transfer evidence (the current curriculum model already has a useful version of these dimensions)
- reason codes such as “two regrouping errors in the last week”

`ReviewTask`

- one objective, 5–20 minutes, a small item set, due date, and selection reason
- state: planned, started, completed, deferred

The daily screen can then show only three things: **Today**, **Needs Review**, and **Progress**. Subject pages remain available for exploration, but they no longer define the system's architecture.

## OCR is a pipeline, not a single model

```text
camera/upload
  → image quality check + crop/deskew/dewarp
  → identify known app worksheet by QR/page ID
  → layout/region detection
  → OCR candidates with boxes and confidence
  → normalize text/operators/LaTeX
  → associate answers with known items (or propose external questions)
  → deterministic grading
  → confidence/consistency gate
  → parent correction when uncertain
  → confirmed LearningEvents
```

Important rules:

- Preserve the original image, crops, raw OCR, normalized result, confidence, model name/version, and human correction. Otherwise errors cannot be audited or used for later evaluation.
- Never ask a general VLM “is this correct?” when a deterministic evaluator can compare integers, decimals, fractions, units, equations, or multiple-choice options.
- Separate **question transcription**, **handwritten answer transcription**, **question–answer association**, and **grading**. A single “page accuracy” number hides which stage failed.
- If an app-generated page is recognized by QR/page ID, use its stored layout and answer key. Only fall back to full document parsing for external worksheets.
- Low confidence should mean “please confirm,” not “wrong.” False accusations of a child's mistake are more harmful than a missed automation.

## Local OCR options

| Option | Officially supported capability | Mac mini fit | Recommended role |
|---|---|---|---|
| Apple Vision | On-device/offline multilingual text recognition; fast/accurate modes; bounding boxes and confidence. Apple notes that Chinese does not support its language-correction/custom-word feature ([Apple Vision guide](https://developer.apple.com/documentation/vision/recognizing-text-in-images), [request API](https://developer.apple.com/documentation/vision/recognizetextrequest)). | Excellent native baseline; no extra model service. It is text OCR, not a math-expression or worksheet-grading system. | Printed Chinese/English/digits baseline, crop quality check, and fallback candidate generation. |
| GLM-OCR 0.9B | Official project describes text, formula, table, and complex-document parsing; supports Ollama and provides a dedicated Apple Silicon MLX guide ([official repo](https://github.com/zai-org/GLM-OCR), [MLX guide](https://github.com/zai-org/GLM-OCR/blob/main/examples/mlx-deploy/README.md)). The guide says Metal acceleration and 8 GB unified-memory fit. | Best first dedicated-model candidate for this ARM64 Mac; run as an isolated local service. | Primary benchmark candidate for mixed printed text, math, layout, and handwriting. Verify against family worksheets before adoption. |
| PaddleOCR / PP-Structure | Modular OCR, layout, table, and formula pipelines. PP-FormulaNet supports printed and handwritten formulas and a large LaTeX vocabulary ([official PaddleOCR docs](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/index/index.en.md)). | Apple ARM wheels exist, but official macOS PaddlePaddle support is CPU-only ([official install guide](https://www.paddlepaddle.org.cn/documentation/docs/en/install/pip/macos-pip_en.html)). | Accuracy challenger and modular fallback, especially when boxes and independent components matter more than speed. |
| MinerU | Offline document parser producing Markdown/JSON, formulas as LaTeX and tables as HTML; supports images/PDFs, handwriting, CPU and MPS acceleration ([official repo](https://github.com/opendatalab/MinerU)). Its docs explicitly warn not to use Docker on macOS because Docker cannot access MPS/MLX acceleration ([official deployment docs](https://github.com/opendatalab/MinerU/blob/master/docs/en/quick_start/docker_deployment.md)). | Good for multi-page external worksheets or textbook ingestion; heavier than needed for a single known answer sheet. Install natively, not in Docker. | Phase-2 batch/document parser, not the first real-time answer checker. |
| GOT-OCR 2.0 | Unified end-to-end OCR for plain/formatted text and region/crop prompting; the official paper covers text, formulas, tables and other visual “characters” ([official repo](https://github.com/Ucas-HaoranWei/GOT-OCR2.0), [paper](https://arxiv.org/abs/2409.01704)). | Valuable research baseline, but the official setup is CUDA-oriented; llama.cpp/ONNX/MNN links on the repo are community contributions. | Benchmark only unless it clearly beats the simpler supported paths on the local dataset. |
| Ollama / llama.cpp vision serving | Ollama accepts images via a local API ([official vision docs](https://github.com/ollama/ollama/blob/main/docs/capabilities/vision.mdx)); llama.cpp's `libmtmd` supports vision architectures using a model plus architecture-specific `mmproj`, but describes multimodal support as fast-moving/experimental ([official docs](https://github.com/ggml-org/llama.cpp/blob/master/tools/mtmd/README.md)). | Convenient serving layer and model swap boundary. Ollama's published GLM-OCR package is about 2.2 GB ([official model page](https://ollama.com/library/glm-ocr/tags)). | Deployment adapter, not an accuracy guarantee. Pin runtime/model versions and re-run evaluation after upgrades. |
| Mathpix | Cloud API recognizes printed/handwritten STEM text, formulas, tables and stroke data, returning Mathpix Markdown/LaTeX and confidence ([official docs](https://docs.mathpix.com/)). Requests require credentials and go to `api.mathpix.com` ([authentication](https://docs.mathpix.com/reference/authentication)). | Not local/offline. Sending a child's worksheet off-device creates privacy, retention, connectivity, and cost decisions. | Optional paid reference benchmark or explicit opt-in fallback only. |

Benchmark claims from vendors should not pick the model. [OmniDocBench](https://github.com/opendatalab/OmniDocBench) is useful because it separately evaluates text edit distance, formula CDM, table TEDS, and reading order, but the real acceptance set must match P4 worksheets and the child's handwriting.

## Mac mini deployment shape

The checked environment is `arm64`, macOS 15.7.3. Unified-memory size was not available from the current execution context, so use RAM tiers:

- **8 GB:** Apple Vision plus GLM-OCR 0.9B/MLX; one request at a time; keep only one VLM resident.
- **16 GB:** same default, with room for a second challenger process during offline benchmarking; do not keep multiple VLMs hot in production.
- **24 GB or more:** MinerU/MLX becomes practical for multi-page batch work, but latency and accuracy must still justify the added complexity.

Keep the Go application as the product/API layer and add an isolated `ocr-worker` process:

- local-only HTTP or Unix socket;
- asynchronous jobs (`queued → running → needs_review → accepted/rejected`);
- model adapter interface with a stable internal JSON schema;
- one process supervisor and health endpoint;
- bounded upload size/page count/concurrency;
- originals and derived crops outside the web root;
- model/version/checksum recorded on every result;
- easy disable switch so learning features work when OCR is unavailable.

Do not place model-specific response formats in the Go handlers or SQLite tables. Normalize them in the worker adapter so GLM-OCR, Vision, PaddleOCR, or a future model can be swapped without changing learning logic.

## Evaluation before integration

Build a small family-specific gold set before choosing a model. A useful first set is 200–400 regions from 40–60 pages, stratified by:

- clean print, phone shadows, skew, folds, low contrast;
- Chinese instructions, English word problems, digits/operators;
- horizontal arithmetic, long-form algorithms, fractions, decimals/money, units;
- tables/graphs and geometry labels;
- neat, rushed, erased, overwritten, and teacher-marked handwriting;
- app-generated worksheets versus external school worksheets.

Split by page/session, not random crop, to avoid near-duplicate leakage.

Acceptance metrics:

| Layer | Metric | Initial decision rule |
|---|---|---|
| Capture/layout | usable-page rate; answer-region recall; question–answer association accuracy | Region recall and association matter more than pretty Markdown. Report by worksheet type. |
| Text | character error rate by Chinese, English, digits, operators | Digits/operators must be reported separately; one changed sign changes the grade. |
| Math | normalized LaTeX edit plus semantic/AST equivalence | Prefer semantic equality (`1/2 = 2/4`) over string equality where the task allows it. |
| Grading | correct/incorrect accuracy, false-wrong rate, abstention rate | Set a very low false-wrong target; uncertain cases must abstain. |
| Confidence | precision at auto-accept threshold; calibration error | A confidence number is useful only if it predicts failures on local data. |
| Product | parent correction time; percentage requiring review | Automation wins only if confirmation is faster than manual entry. |
| Runtime | cold/warm latency, pages/minute, peak memory, crash rate, thermal behavior | Measure on the actual Mac mini with the server running. |

Suggested launch gate for automatic grading: at least **99.5% precision among auto-accepted answer transcriptions**, with all other cases routed to confirmation. This is a product safety target, not a claim that any current model reaches it.

## Phased delivery

### Phase 0 — unify the learning experience

1. Define stable skill IDs and map current curriculum topics, drills, mistakes, and diagnostics to them.
2. Introduce the append-only learning-event contract behind adapters; leave existing tables intact.
3. Produce one weekly plan and one daily review queue across math activities.
4. Show parents “evidence → diagnosis → next action,” not a collection of feature histories.

Success: the system can answer “what should she do for 15 minutes today, and why?” without OCR.

### Phase 1 — worksheet identity and manual confirmation

1. Add QR/page IDs and known answer boxes to worksheets generated by the app.
2. Upload/capture a page, detect its identity, display answer crops, and let a parent type/confirm results.
3. Store capture artifacts and confirmed events using the future OCR schema.

Success: end-to-end data flow and UX work before model risk is introduced.

### Phase 2 — local OCR pilot

1. Implement Apple Vision baseline and GLM-OCR/MLX worker adapter.
2. Run the gold set; add PaddleOCR only if it can materially improve a weak category.
3. Auto-fill answers but require confirmation; collect corrections and latency.
4. Enable auto-accept only for categories that pass the precision gate.

Success: OCR saves parent time and never silently contaminates mastery data.

### Phase 3 — external worksheets and remediation

1. Add full-page layout parsing for school worksheets, optionally using MinerU for batches.
2. Match questions to the item bank where possible; create reviewed imported items where not.
3. Convert confirmed mistakes into misconception tags and targeted 3–5 question re-practice.
4. Re-check later with a different representation, not a near-duplicate.

Success: “photo → verified mistake → focused re-teach → re-check” is a closed loop.

### Phase 4 — optional local tutor

Use a local VLM/LLM to phrase hints or explanations only after the item, expected solution, learner response, and misconception are structured. Require grounded output and keep deterministic grading authoritative. Measure whether hints improve the next unaided attempt; conversational fluency alone is not success.

## Decisions to avoid

- Do not start by scraping or buying a huge question bank. First make 200–500 high-quality, tagged, evaluable P4 items serve the loop well.
- Do not let every subject invent its own mastery status or review scheduler.
- Do not infer “personalization” from a VLM chat response. Personalization is selection from observable evidence under explicit curriculum constraints.
- Do not train/fine-tune first. Establish a labeled local benchmark and error taxonomy; most early gains will come from page identity, cropping, normalization, and deterministic evaluation.
- Do not expose the OCR service to the LAN by default or store child images indefinitely. Define retention, deletion, and export before routine use.
- Do not promise answer recognition for free-form working based on printed-text OCR results. Handwriting, equations, spatial long-form work, and crossed-out answers are separate evaluation strata.

## First concrete milestone

The highest-leverage next milestone is not an OCR demo. It is a **P4 weekly learning loop** backed by stable skills and attempt events:

1. Monday: 8–12 question diagnostic sampler.
2. Tuesday–Thursday: one concept block, one fluency block, one short review block.
3. Friday: transfer check using unfamiliar representations.
4. Parent view: three strengths, up to two concerns, exact evidence, and next week's plan.

Once that loop works with on-screen and manually confirmed worksheet answers, OCR can plug into it cleanly. Otherwise OCR will only make the current fragmentation faster.
